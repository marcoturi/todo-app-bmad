## Challenges and Struggles

### 1. Schema and Types Written in `apps/api` Instead of `packages/shared` (Recurring)

**What happened:** During backend development, TypeBox schemas and response types were repeatedly defined inline in `apps/api` rather than in `@todo-app/shared`. Marco had to manually intervene multiple times to correct the location.

**Root cause:** Dev notes described the correct pattern, but no acceptance criterion _verified_ that `@todo-app/shared` was the source of truth. The path of least resistance (write the schema next to the route) kept winning over the architecturally correct pattern. A rule stated as a note is advisory; a rule enforced by an AC or a ❌ is a gate.

**Impact:** Unplanned manual rework by Marco. Silent drift risk between API runtime schema and shared types.

### 2. Standalone QA Stories (2.5, 2.6) Separated Testing from Implementation

**What happened:** Stories 2.5 and 2.6 were standalone verification stories — testing was a separate work item from implementation rather than a first-class part of each feature story's definition of done.

**Root cause:** Epic 2's story decomposition inherited a "build first, test separately" mental model. This implied that feature stories could be `done` before E2E tests existed — which is incorrect.

**Impact:**

- Story file status drift: 2.3 and 2.5 headers show `review` while sprint-status shows `done`.
- Created a temptation to defer E2E work when the feature felt "done enough".
- Story 2.5 still surfaced configuration issues that should have been caught during 2.1 and 2.2 implementation.

### 3. Subtle Backend Runtime Gotchas (Required Dev Notes, Not Discoverable Otherwise)

- postgres.js auto-converts `TIMESTAMPTZ` → `Date` objects (not strings) — `TodoModel` must reflect this.
- `SqlRepositoryBase.insert()` returns `void`, not the inserted row — handler must return the original `TodoEntity`.
- TypeBox `example` keyword AJV conflict — `buildApp()` requires `ajv.customOptions.keywords: ['example']`.
- 10ms delay between DB inserts required in E2E to ensure distinct `created_at` for ordering assertions.

These were handled correctly but only because they were explicitly documented. Without the Dev Notes, all four would have been rediscovery work.

### 4. Non-Obvious RTK Query Behaviour (Story 2.3)

- Endpoint paths must NOT start with `/` when using `fetchBaseQuery` with a trailing-slash `baseUrl`.
- `injectEndpoints` on `baseApi` — NOT `createApi`. Injected endpoints share the existing `api` reducer automatically — do not add a separate reducer key.

## Key Insights

1. **Rules need to be enforced structurally, not stated conventionally.** "Check shared first" (advisory) failed repeatedly. "Never define response schemas in apps/api — ❌ rule in project-context.md" (structural gate) will not. The fix lives in `project-context.md` which every agent reads before touching code.
2. **Testing is not a phase — it is part of the feature.** Every story must own its unit tests and E2E tests as acceptance criteria. The only valid split is by architectural layer (BE story + its tests; FE story + its tests), never "feature story" + "testing story".
3. **Dev Notes propagation remains a genuine strength.** The pattern of documenting gotchas (runtime behaviour, timing issues, AJV conflicts) inside story files worked — knowledge transferred cleanly between stories without rediscovery.
4. **When all Epic 1 retro items are addressed before the next epic begins, the epic runs smoother.** No carryover debt, no surprise blockers.
